# Upgrading from 0.22 to 0.23

0.23 closes the engine's surface: what an operation takes, answers and writes is declared in one schema language and checked, and a handler reaches the engine only through its context. It also lets plugins be given by module, configured by one `env` and handed the host's `services`, so expensive reads can run in a pool of workers built from the app's own plugins (sections 9 and 10). Most changes are mechanical; each section says what to change and how you will notice if you miss it, and the checklist at the end lists them all.

## 1. Declarations are TypeBox schemas

Args, returns and table columns are [TypeBox](https://github.com/sinclairzx81/typebox) schemas, re-exported as `Type` from `vex-core` and `vex-core/framework`. The old string forms are refused as the engine starts and do not compile.

| 0.22 | 0.23 |
| --- | --- |
| `args: { id: "string" }` | `args: { id: Type.String() }` |
| `"number?"` | `Type.Optional(Type.Number())` |
| `"json"` | `Type.Unknown()`, or a precise schema (`Type.Array(Type.String())`) |
| a value that may be `null` | `Type.Union([Type.String(), Type.Null()])`: null is a value, never "absent" |
| `columns: { n: { type: "number", optional: true, index: true } }` | `columns: { n: Type.Optional(Type.Number({ index: true })) }` |
| `{ type: "string", default: "", renamedFrom: ["text"] }` | `Type.String({ default: "", renamedFrom: ["text"] })` |
| `type: "any"` | `Type.Unknown()` (stored as JSON text) |

A handler's `args` are typed from its declaration, a plugin's and a file's (`query`, `mutation`, `action` in `vex-core/framework`) alike.

## 2. Calls, answers and writes are checked

- **Args:** a call with an undeclared arg, a missing one, or one of the wrong type is refused, naming every problem (HTTP 400, `ArgsError`). In 0.22 an undeclared arg was ignored: callers that sent extra fields now fail. An `undefined` value counts as not given.
- **Answers:** an answer is JSON data (a `Date`, `Map`, class instance or function is refused), and one against a declared `returns` is refused; a refused mutation commits nothing. Every caller, in process or over the wire, a call or a subscription, is handed the answer as JSON reads it back: an `undefined` property is gone, `-0` is `0`.
- **Writes:** every insert, update and upsert passes the table's columns: required columns given, each value of its column's type, no undeclared column.

## 3. Query and mutation contexts

| 0.22 | 0.23 |
| --- | --- |
| `Date.now()` in a query | `ctx.now(resolutionMs)`: a subscription re-runs when the next interval begins |
| `Date.now()`, ids, random in a mutation | `ctx.now()` (one time for the call), `ctx.id()`, `ctx.random()` |
| `ctx.runtime` in a query or mutation | gone; job controls are an action's (`ctx.runtime`) |
| `ctx.db.sql(sql, ...params)` in a query | `ctx.db.sql(reads, sql, ...params)`: name every table the statement reads, held to rows (`{ t: filters }`) or whole (`{ t: "all" }`) |
| `ctx.db.sql` in a mutation | reads and row changes only (`SELECT`, `INSERT`, `UPDATE`, `DELETE`, ...); schema changes are migrations |
| calling another query by `vex.query` from a handler | `ctx.query(name, args?, { user }?)` |
| I/O or a follow-up effect in a mutation | `ctx.scheduler.runAfter(ms, name, args)` / `runAt`: runs once, only if the mutation commits |

A query reading state its context does not track goes stale; `purityCheck: "always"` (in tests) or a share of runs finds it.

## 4. Jobs and webhooks are actions

A job's and a webhook's handler receives an `ActionContext`: no `ctx.db`. Read and write through `ctx.query` and `ctx.mutate`, each a transaction of its own:

```ts
// 0.22
api.registerJob("sweep", { schedule: "every 1h", handler: (ctx) => ctx.db.table("t").delete() });

// 0.23
api.registerMutation("clear", { args: {}, handler: (ctx) => ctx.db.table("t").delete() });
api.registerJob("sweep", { schedule: "every 1h", handler: (ctx) => ctx.mutate("app.clear") });
```

## 5. The engine's surface

| 0.22 | 0.23 |
| --- | --- |
| `vex.use(middleware)` | `api.use(middleware)` in a plugin, declared before the engine starts |
| `vex.readTable(table)` | an operation, or `rawSql` from `vex-core/internal` in tests and tooling |
| `vex.unsafeSql`, `unsafeGetStorage`, `unsafeBulkInsert` | `rawSql(vex, ...)`, `rawStorage(vex)`, `rawBulkInsert(vex, ...)` from `vex-core/internal`, for tests and tooling; what they write is announced |
| schema changes by raw SQL at boot | `VexOptions.migrations`: `[{ id, up(m) }]`, each applied once, in order, in a transaction, before the engine serves |

## 6. Handlers reach the engine through their context

A handler calling the engine directly (`vex.query` inside a query, mutation or action) is refused with `ReentryError`, naming the context call to use instead. Middleware is not a handler and may call the engine.

Code a handler calls that holds the engine itself (a service object, a helper) takes the handler's context instead; an action's context satisfies the engine's `query` and `mutate`. Work a service starts from a handler and that outlives it (a background run, a queue) runs in the service's own async scope, created where the service is (`new AsyncResource(name)`), so it is not the handler's.

## 7. Callers and subscriptions

- A caller (`{ user }`) is plain data; one holding a function is refused.
- Subscriptions to one query with one set of args share a run among callers alike in every field the query's runs read of them; a caller differing in a field a run reads gets its own.
- `subscribe(..., { onError(error, ended) })` hears a failed run (`ended: false`, the last answer stands) or a view outgrowing its budget (`ended: true`).

## 8. The engine's tables

`_jobs`, `_migrations` and `_scheduled` are the engine's to write: `ctx.db` refuses a write to one, through the builder or SQL. `_scheduled` is not read through `ctx.db` either. `_spans` stays the app's.

## 9. Plugins, settings and services

Nothing here is required to upgrade: a plugin given by value, configured by its factory's arguments, runs as before. It is what a pool of read workers (section 10) requires, and what keeps a plugin's code free of the host's objects.

| 0.22 | 0.23 |
| --- | --- |
| `plugins: [notesPlugin({ dataDir, mailer })]` | `plugins: [new URL("./plugins/notes.ts", import.meta.url)]`: the module's default export is the plugin (a function, a definition, or an array of them). An absolute path or a package name works too; a relative path string is refused. |
| a setting passed to a plugin factory (`dataDir`, a key, a URL) | `VexOptions.env`: one object of plain data, read as `ctx.env` in every context and `api.env` at registration |
| a live object passed to a plugin factory (a client, a fleet, a lazy `() => vex`) | `VexOptions.services`, read as `ctx.services` in actions, jobs and webhooks; a query or mutation that used one becomes an action, or schedules one (`ctx.scheduler`) |
| a callback a plugin fires after a write (`onCreated`) | the mutation schedules an action (`ctx.scheduler.runAfter(0, ...)`), which uses `ctx.services` |
| a value that changes while the server runs, read through a closure | a table its owner writes, so reads of it are tracked |

Type both once, by augmenting `VexEnv` and `VexServices` (`declare module "vex-core" { interface VexEnv { ... } }`); `Vex.create` then requires what they declare. An `env` holding anything but plain data (a function, a `Date`, a class instance) is refused as the engine starts, naming where.

A plugin module's top-level code runs once per thread that imports it: a module-level `Map`, cache or client is one per thread.

## 10. Reads off the main thread

`VexOptions.evaluation: { workers, offloadAboveMs? }` runs expensive reads in a pool of workers, each building a read-only engine from the app's own plugin modules, `env` and database (`StorageAdapter.reader()`). A query's runs, subscriptions' and one-shot `vex.query` calls alike, go to the pool once their average passes `offloadAboveMs` (2 ms unless set; 0 sends every run) and come back under half of it. Writes, actions and `services` stay on the main thread, and so do reads under `purityCheck`.

`Vex.create` refuses a pool when a plugin is given by value or the storage has no `reader()` (a database in memory): a worker builds its engine from the main engine's own options. A file-based app is given by a module whose default export is `(await scanDirectory(dir)).plugins`.

A refusal thrown in a worker reaches the caller with its `HttpError` status, body and headers; any other error, with its name and message (an `instanceof` check of another class does not hold across).

## 11. Dependencies

`vex-core` depends on `typebox ^1.4.3` and no longer on `nanoid`.

## Checklist

Required to upgrade:

1. Every `args`, `returns` and column is a TypeBox schema (section 1).
2. Callers send only declared args; answers and caller objects are plain data (sections 2, 7).
3. `Date.now()`, random and ids in queries and mutations come from the context; queries name what their raw SQL reads; mutations' raw SQL changes rows only (section 3).
4. Jobs and webhooks read and write through `ctx.query` and `ctx.mutate` (section 4).
5. `vex.use`, `readTable` and `unsafe*` are replaced; schema changes are migrations (section 5).
6. No handler calls a captured engine: it uses its context, and services that outlive a handler run in their own async scope (section 6).
7. No handler writes `_jobs`, `_migrations` or `_scheduled`, or reads `_scheduled` (section 8).

To run reads off the main thread, in addition:

8. Each plugin is a module whose default export is the plugin (section 9).
9. Plugin settings move to `env`; live objects to `services`, used from actions only (section 9).
10. Queries that read process memory (a module's map, a closure's state) read a table instead: in a worker that memory is another copy (section 9).
11. `evaluation: { workers }` on a storage with a `reader()` (section 10).
